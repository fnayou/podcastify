# Contributing

## Development Setup

1. Clone the repository:
   ```bash
   git clone https://github.com/fnayou/podcastify
   cd podcastify
   ```

2. Install Task (go-task):
   ```bash
   # macOS
   brew install go-task

   # Linux
   sh -c "$(curl --location https://taskfile.dev/install.sh)" -- -d
   ```

3. Check the environment, then create the virtualenv, install the requirements and the commit hook:
   ```bash
   task doctor
   task dev:setup
   ```

   `task dev:setup` creates `.venv`, installs `requirements.txt` and `requirements-dev.txt` into it, and runs `task dev:hooks`. The test tasks use `.venv/bin/python` when it exists.

Tasks that only you need can go in a `Taskfile.dev.yml` at the repository root. It is optional, git-ignored, and its tasks appear under the `devlocal:` prefix.

## Workflow

### Parallel work

Several tickets in parallel use worktree lanes: `task worktree:install` once, then see [worktree lanes](worktree-lanes.md).

### Build and test locally

```bash
# Start the container
task docker:up

# Generate feeds
task podcastify:generate

# View logs
task docker:logs
```

### Audio test fixtures

Duration tests read the small files in `tests/fixtures/audio/` (1 s each). To rebuild them, run `tests/fixtures/make_audio.sh`; it needs Docker and runs ffmpeg in a throwaway container. CI does not run it, and the image has no ffmpeg. See [ADR 0006](adr/0006-tinytag-for-durations.md).

### Documentation site and generated art

A public documentation site (`website/`, built with Zensical and published on GitHub Pages) is planned; `docs/` stays internal and is not published. The decisions are recorded in [ADR 0008](adr/0008-docs-site-art-and-index-page.md). The site pieces are not built yet: the site content (#117) and the build and deployment (#118).

The brand art (logo, favicon, README banner, social preview and the architecture diagram) is generated by `tools/art/`. Check it with `task art:check`, rebuild it with `task art:build` and commit the images in `website/assets/images/`; the test suite fails when a committed SVG is stale. See the [art setup guide](guides/art-setup.md).

### Configuration reference

The field tables in [Configuration](configuration.md#fields) are generated from the pydantic models in `podcastify/parser.py`, so they cannot drift from the code. Every model field carries a `Field(description=...)`; a test fails when one is missing. The text between `<!-- BEGIN GENERATED: fields -->` and `<!-- END GENERATED -->` is rewritten by `tools/config_reference.py`; the prose, examples and behaviour notes around it are hand-written.

After you add or change a field or its description, refresh the page and commit it with the model change:

```bash
task docs:reference            # rewrite the region
task docs:reference CHECK=1    # change nothing; exit 1 with a diff when the region is stale
```

The freshness test (`tests/test_config_reference.py`) regenerates the region in memory and fails when the committed page differs. The tool needs the project requirements, so it uses `.venv` when `task dev:setup` created it. A legacy key shown as deprecated is listed in `ConfigReference.DEPRECATED`, because the models cannot express that.

The tool takes the page path from `--page` (default `docs/configuration.md`). The page will move to `website/` with the public site (#117); only the default changes then.

### Add a new podcast for testing

```bash
task podcastify:new NAME=testshow
# place MP3s in public/testshow/
task podcastify:generate
```

### Clean up

```bash
task docker:down
task podcastify:clean:feeds
task docker:clean
```

`task docker:clean` removes only this project's containers, networks and volumes. `task docker:pull` rebuilds the image with freshly pulled base images.

## Code Style

- Python: 4-space indent, UTF-8, LF line endings
- YAML: 2-space indent
- `podcastify/` package with thin `app.py` entry point
- PascalCase for classes, snake_case for functions
- No unused imports or dead code

`ruff` lints and formats Python (config in `pyproject.toml`), and `hadolint` lints the Dockerfile. Both run as pre-commit hooks (`task dev:hooks`) and in the CI `test` job. To check everything at once: `.venv/bin/pre-commit run --all-files`. The hadolint hook needs Docker.

## Commit Conventions

[Conventional Commits](https://www.conventionalcommits.org/): `<type>[scope][!]: <description>`.

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Mark breaking changes with `!` or a `BREAKING CHANGE:` footer.

```
feat(rss): add season/episode numbering support
fix(parser): resolve image URL when using absolute paths
docs: update deployment guide with nginx example
```

The `commit-msg` hook checks this locally (`task dev:hooks`). The `commits` CI check validates the PR title and every commit subject.

## Pull Requests

`main` is protected: no direct pushes, no force-push, linear history. A PR needs the `test`, `docker` and `commits` checks green, and merges by rebase only.

1. Create a branch from `main`: `git checkout -b feat/my-feature`
2. Make your changes
3. Run `task dev:validate`
4. Commit with the conventional format
5. Push and open a PR titled in the same format

## Releases

Releases are git tags in the form `vYYYY.M.PATCH` (CalVer, for example `v2026.10.0`), pushed by the owner. The tag format, the Docker Hub tags, the provenance and the release notes are recorded in [ADR 0007](adr/0007-calver-and-release-policy.md). The helper `task release:tag` computes and creates the tag (see "Make a release" below). Release notes are published on [GitHub Releases](https://github.com/fnayou/podcastify/releases).

The Docker Hub overview is synced from `README.md` on each stable release (not on prereleases); the short description is the image's OCI description label. If the sync step is red, the release is fine: the step never blocks it. The owner then checks the token rights: the `DOCKERHUB_TOKEN` secret must belong to a token that can edit the repository overview (read/write/delete scope, and Admin rights on the repository if it belongs to an organisation). Keep the links in `README.md` absolute (`https://github.com/fnayou/podcastify/blob/main/...`), because Docker Hub does not resolve relative ones.

The notes are generated from the commit subjects by [git-cliff](https://git-cliff.org) with the root `cliff.toml`, so a clear Conventional Commit subject is the release note. `feat`, `fix`, `perf`, `build` and `revert` are listed; `ci`, `docs`, `chore`, `test`, `style` and `refactor` are hidden; `build(deps)`, `ci(deps)` and `chore(deps)` are folded into one "Dependencies" line; a `!` or a `BREAKING CHANGE:` footer puts the commit under "Breaking Changes", whatever its type; merge commits and non-conventional subjects are skipped. The range is the commits since the previous CalVer tag (a stable release skips release candidates when it looks for that tag), and `f1e964de..<tag>` for the first CalVer release. The release job fails when the notes are empty. `CHANGELOG.md` is frozen history and is not edited.

Preview the notes of the commits on your current checkout:

```bash
task release:changelog                  # as the next stable release
task release:changelog TAG=v2026.10.0   # an existing tag, as the release job sees it
```

The task runs a pinned git-cliff image in a throwaway container with the repository mounted read-only, so nothing is installed on the host. It needs Docker and uses the same `cliff.toml` and range rules as `release.yml`. When you change the git-cliff version, change it in `tasks/release.yml` and in the `version` input of the git-cliff step in `release.yml` together.

### Make a release

1. Merge the pull requests for the release to `main` and wait for the `CI` run of the merge commit to be green.
2. On an up-to-date `main` (clean tree, `HEAD` equal to `origin/main`), run `task release:tag`. Add `PRERELEASE=rc` for a release candidate. To rehearse from any branch without creating anything, run `task release:tag -- --dry-run`.
3. The helper fetches `main` and the tags, refuses unless the checks above hold and the latest `CI` run for `HEAD` is green (the CI check is skipped, with a note, when `gh` is not installed), and prints the proposed tag and the release notes preview from `task release:changelog`. Review the notes.
4. Answer `y` to create the annotated tag `Release <tag>` locally. Any other answer creates nothing.
5. The helper never pushes. Run the `git push origin <tag>` command it prints.
6. Watch the `Release` workflow: `validate-tag`, `notes-check`, `test`, `docker`, `release`.
7. Check the Docker Hub tags (`YYYY.M.PATCH` and, for a stable release, `latest`), the Docker Hub overview and the GitHub Release page (notes, the three `docker` lines, prerelease flag for a candidate).

The next tag is `vYYYY.M.PATCH` for the current UTC month, where `PATCH` is the highest stable `PATCH` already tagged in that month plus one, or `0`. The `PATCH` is compared as a number, so `9` is followed by `10`. Tags that are not CalVer-shaped (`v1.x`, `1.0.1`) are ignored. A release candidate tag (`-rc.N`) never counts as the holder of a `PATCH`: with `v2026.10.0-rc.1` and no stable tag, the next stable tag is `v2026.10.0`, not `v2026.10.1`. `PRERELEASE=rc` proposes the next candidate of the next stable tag, numbered from `rc.1`.

If a release fails:
- Before the image is pushed (`validate-tag`, `notes-check`, `test`, or a red `docker` job before the push step): nothing is published. Fix the cause on `main`. Delete the bad tag locally and on `origin` (`git tag -d <tag>` and `git push origin :refs/tags/<tag>`), a deliberate owner action, then run `task release:tag` again; it proposes the same tag.
- After the image is pushed (the `release` job is red): the image is public, so do not reuse the tag. Create the GitHub Release by hand from the tag with the notes from `task release:changelog TAG=<tag>`, or fix the cause and release the next `PATCH`.
- A red "Sync Docker Hub overview" step does not fail the release; see the token note above.

## CI time budget

CI execution time is a requirement. A PR must not push any workflow past its budget. Every PR that touches `.github/workflows/` reports the job durations before and after the change in its description.

| Scope | Baseline (median) | Budget |
|---|---|---|
| CI `test` job | 24 s | 60 s |
| CI `docker` job | 2 min 07 s | 3 min |
| PR total (CI wall time, `test` start to `docker` end) | 2 min 32 s | 4 min |
| Release (all jobs, wall time) | 3 min 46 s | 6 min |

Baseline measured on 2026-10-23 with `gh`: median of the last 8 successful CI runs on PRs to `main` (`test` 11 to 45 s, `docker` 1 min 44 s to 2 min 31 s), and the last release run, `v1.1.1` (`test` 35 s, `docker` 3 min 01 s, `release` 4 s).

To see the durations of the latest runs:

```bash
task ci:durations           # last 5 successful CI and Release runs
task ci:durations LIMIT=8
```
